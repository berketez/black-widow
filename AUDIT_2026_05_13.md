## YÖNETİCİ ÖZETİ (TL;DR)

**1. v1.10-v1.15 boyunca yazılan tüm step registry yatırımı, default kullanıcıda çalışmıyor.** `use_step_registry=False` default; hacker_cli flag'i set etmiyor. Yeni pipeline kodu (registry+runner+context) örnek niteliğinde temiz ama eski `stages.py` monolithic kodu (L4349-5500, ~1100 satır) hâlâ asıl çalışan yol.

**2. v1.15-B/C/D step'leri (TRex, PDB, BinaryNinja) PipelineRunner'a kondurulmamış.** Son 4 commit'in (~600 satır kod + 22 test) bir tanesi bile gerçek analiz akışında tetiklenmiyor.

**3. F1=1.0 sahte ölçüm hâlâ aktif.** v1.11.0 P4 "preserved" patch yetersiz; GT döngüsü sadece nm export'larında dönüyor, FUN_xxx iç fonksiyonlar (libsqlite3'te 2348 adet) hiç ölçülmüyor. `renamed_total=0` durumda F1=global_f1 atanıyor → yalan.

**4. Performans 30-40 MB binary için yetersiz.** Perf ajanı 67 KB binary'de static stage'i 60s/819 MB RSS ölçtü. Ama Berke'nin 30-40 MB binary üzerindeki **pratik ölçümü ~2 saat** (ekstrapolasyon yanıltıcıydı). Claude Code (~150-300 MB) **1 gün** sürmüştü. Detaylı perf tablosu için aşağıdaki "Performans Yol Haritası" bölümüne bak.

**5. v1.20.5 6 borç listesi revize edilmeli.** Mevcut liste eksik 4 madde (DWARF kanalı, demangler wire, LLM4Decompile sil, network default OFF) ve 1 yanlış sıralama içeriyor.

## PERFORMANS YOL HARİTASI (2026-05-13 ölçümler + tahminler)

### Mevcut durum (Wave 1 sonrası, Wave 3 perf optimizations ÖNCESİ)

| Binary boyutu | Tipik örnek | Berke'nin pratik ölçümü | Tahmini RAM peak |
|---|---|---|---|
| 67 KB | echo (coreutils) | 60s (perf ajanı) | 819 MB |
| 30-40 MB | Chrome komponenti | **~2 saat** | ~4 GB |
| 150-300 MB | Claude Code (Electron) | **~1 gün** | ~25-40 GB (swap'a düşmüş olabilir) |

### Mevcut bottleneck dağılımı (30-40 MB binary için, ~120 dk toplam)

| Aşama | Süre | Sebep |
|---|---|---|
| Static analyzers (sigdb match) | ~60-80 dk | `_match_by_strings` O(F×M×K) Python loop, `_match_by_bytes` masked Python compare. 30 MB binary'de ~10K fonk × ~10K sig × ~5 keyword = milyarlarca substring op |
| Ghidra decompile (3 ayrı invocation) | ~30-50 dk | Her invocation JVM cold start 5-8s + 30 MB analyze 10-15 dk × 3 |
| Naming/reconstruct | ~15-25 dk | C output üstünde regex + Aho-Corasick-olmayan rename |
| Pipeline overhead + sigdb init | ~5-10 dk | Sequential runner, sigdb 11.5s her CLI invocation |

### Wave 3 optimizasyonları (v1.20.5 hedefi)

| Optimizasyon | Kazanç | Pratik açıklama |
|---|---|---|
| **B14 string Aho-Corasick + inverted index** | **-50 dk** (60 → 10 dk) | Python loop → C-accelerated AC. Literatürde norm 30-50× hız. En büyük tek kazanç. |
| **B15 byte Aho-Corasick** | **-30 dk** (40 → 10 dk) | Aynı pattern, byte matching için. Wildcard-free pattern'lere AC, wildcard'lılar ayrı küçük trie |
| **B16 pipeline paralelizm (M2)** | **-20-30 dk** | Ghidra+TRex+BN+PDB step'leri concurrent. Topological independent set scheduler |
| **JVM reuse / Ghidra Bridge** | **-15-20 dk** | 3 invocation → 1 persistent JVM (cold start tek seferde) |
| **B9 LMDB complete migration** | **-3-5 dk** | JSON 1.4 GB parse + dict load yerine LMDB readonly lookup |
| **TOPLAM** | **~120-135 dk** | **2 saat → 15-25 dk** |

### Notlar

- Wave 3 tahminleri **agresif değil**, standart RE araç teknikleri:
  - Hex-Rays/IDA Pro Aho-Corasick kullanıyor (FLIRT zaten AC patenti)
  - BinaryNinja persistent worker pool kullanıyor
  - Ghidra Bridge (persistent JVM) bilinen pattern
- "10-15 dk" perf ajanı tahmini iyimser. Gerçekçi tahmin: **15-25 dk** (6-8× hız mevcuda göre)
- Eğer Wave 3 sonrası 25 dk altına inmezsek, algoritma seçimini gözden geçirip dönüş yapacağız (büyük olasılıkla `pyahocorasick` yerine custom C extension veya Rust binding)
- 800 MB için **distributed mode** zorunlu; tek makinede streaming+sharding bile ancak 4-6 saatte çıkar. v3.x hedefi.
